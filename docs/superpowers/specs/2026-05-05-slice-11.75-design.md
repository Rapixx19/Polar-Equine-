# Slice 11.75 — Bluefy + capture-quality UX guard rails (~3.5 h)

**Status:** design approved 2026-05-05; awaiting file-level approval before implementation.

**Branch target:** off `main` after PR #12 (`f7b4699`) merge.

---

## Context

Phase 3 closed (algo 0.5.0 live on Railway). Slice 11.6 (PR #12) replaced magic-link auth with email+password and unblocked iPhone Bluefy as the primary capture browser. The first end-to-end smoke on iPhone Bluefy + H10 succeeded (`session_id 0113a8ae-09e9-4db1-a7fc-8e40b8073e6b`, full metrics row including TRIMP + recovery τ).

That smoke also exposed three gaps that a non-technical tester (Ferdinand's sister, the first real rider) will hit before her first session ends:

1. **Screen-lock pauses BLE silently.** iOS Web Bluetooth halts notifications when the screen locks or Bluefy backgrounds. The rider sees no error; samples just stop landing in `samples_hr`.
2. **No live capture-quality signal.** The smoke session returned `rr_cleaning_quality = 0.46` (about half the beats corrected by Lipponen-Tarvainen). The rider had no in-the-moment feedback that the strap was making poor contact — they only learned post-facto from the metrics row.
3. **iOS Safari users hit a dead end.** The current `UnsupportedBanner` says "iOS support coming in V.0.1" but Bluefy already works; it should redirect.

This slice ships three guard rails (A + B + C from the brainstorm). It does **not** ship D (BLE auto-reconnect on disconnect events) — that work requires a real-flake test environment and is deferred to a future slice with a documented prerequisite.

**Goal:** the rider knows in real time whether the recording is good, gets a clear instruction before they lock their phone, and lands on the right browser if they tap an iOS Safari link.

**Done-when:**
- iOS user-agent on `/session/new` sees a soft-warn callout about screen-lock + auto-lock setting (dismissable, sessionStorage-backed)
- On session start, `navigator.wakeLock.request("screen")` is attempted (best-effort, silently no-ops if missing)
- During the session, a 3-state colored badge (🟢🟡🔴) reflects strap contact + RR correction rate, mounted **adjacent to** (not replacing) the existing BLE connection state
- On the saved page, a one-line summary shows what fraction of the session was at each quality state
- iOS Safari (no Web Bluetooth) sees an "Open in Bluefy" message replacing the legacy "iOS coming in V.0.1" copy
- ≥3 vitest cases covering the quality hook (state transitions at thresholds, lost-on-silence, freeze contract) + ≥1 case covering PreSessionGuard iOS detection
- Manual smoke on Bluefy passes the 5-step verification list (incl. the "no false alarms" still-sit test)
- Slice 18 entry in `docs/05-build-plan.md` is updated to document the deferred-D prerequisite

**Kill switches:**
- Wake Lock API rejected by Bluefy → degrade A to soft-warn-only, no behavior change for non-iOS or Wake-Lock-supporting browsers
- Still-sit verification (step 5) shows the 5%/20% thresholds are too tight and the badge flickers 🟢↔🟡 on healthy resting HRV → raise the lower threshold to 7% or 10%, re-test, document the empirical choice in the inline comment
- If implementing eats >5 h (1.5× estimate) → ship A + C only, defer B to a follow-up; the worst case is the rider doesn't see live quality but still gets the end-of-session summary and the screen-lock warning

## Locked decisions (from brainstorm + review refinements)

| Decision | Choice |
|---|---|
| Scope | A (pre-session guard), B (live quality badge), C (end-of-session summary). **D (auto-reconnect) deferred to Slice 18 with explicit prerequisite.** |
| Single source of truth | `useCaptureQuality()` hook feeds both B (live state) and C (cumulative summary). No separate computation paths — prevents B/C semantic drift. |
| Quality state machine | 3 states only: 🟢 good / 🟡 weak / 🔴 lost. No percentages in rider UI (false precision; unreadable on a horse). Percentages live in `data-*` attrs for dev-tools debugging. |
| Lost detection | **Silence-only**: no notifications received in 5 s. The H10 sensor.contact enum (`"unsupported" \| "no-contact" \| "contact"` per `lib/ble/hr-codec.ts`) has no `"bad"` value — `"no-contact"` is the worst hardware signal H10 emits and maps to **weak**, not lost. Therefore the 5-second notification-silence rule is the *only* path to 🔴 in V.0. High correction rate alone never trips lost. |
| Weak detection | `contact === "no-contact"` from H10 native signal **OR** rolling-30 s RR correction rate ≥ 5% (open-ended above; high correction rate is still strap quality, not lost) |
| Good (default) | `contact === "contact"` (or `"unsupported"`, treated as good — older straps that don't report the field) AND rolling-30 s correction rate < 5% AND notifications received within last 5 s |
| RR correction-rate proxy | First-pass artefact gate from **Lipponen & Tarvainen 2019** (J. Med. Eng. Technol.): count consecutive intervals where `|RR_i − RR_{i-1}| / RR_{i-1} > 0.20`. Cheap O(n), suitable for live client-side rendering. Full algorithm has more stages — that work happens algo-side, not in the browser. |
| Pre-session guard behavior | **Soft-warn callout** (inline alert, not a blocking modal). Riders standing next to a 600 kg animal won't navigate iOS settings; blocking creates a frustration trap. The Wake Lock API attempt is the belt-and-suspenders backstop. |
| Wake Lock | Best-effort. Request on session **start** (when the user taps "Start session" in `SessionRecorder`). Release on session end. Re-acquire on `visibilitychange === "visible"` if a session is still active (covers brief tab-switch). The browser implicitly releases the lock on `visibilitychange === "hidden"` so no explicit release is needed there. **Pre-coding step:** smoke-test in Bluefy before relying on it; if absent, A degrades to soft-warn only with no UX change. |
| Badge placement | Mount `CaptureQualityBadge` **adjacent to** the BLE connection state in `ConnectionStatus`, not replacing it. Two distinct concerns: BLE link state vs. signal quality. A device can be `Connected` with `Lost contact` simultaneously. |
| Summary persistence | `sessionStorage.setItem("quality:${sessionId}", JSON.stringify(summary))` keyed by session_id. The saved page reads `quality:${params.id}`. Stale entries from prior sessions are harmless because they're keyed and never collide. No cleanup logic needed. |
| Summary freeze | Hook exposes `freeze()` called from `SessionRecorder.stop()`. After freeze, the cumulative summary is immutable — no drift if the user pauses on the saved page and comes back. Tested explicitly. |
| Pre-session copy (refined) | *"Keep your screen on during the ride. Lock your phone and Bluetooth pauses, which can interrupt recording. (Tip: Settings → Display → Auto-Lock → Never.)"* — one rider-facing sentence, one why, one parenthetical tip. |
| iOS Safari fallback | Rewrite `UnsupportedBanner` copy to "Open this page in Bluefy to record sessions on iOS." No deep-link scheme (`bluefy://`) for V0.0 — too fragile across iOS versions; instructions are enough. |

## Architecture

```
HRSample stream (existing) ─┐
H10 sensor.contact (existing)─┼──► useCaptureQuality() ──┬──► <CaptureQualityBadge />          (B, live)
                              │   ├─ rolling 30 s window  └──► sessionStorage[quality:${id}]   (C, cumulative)
                              │   └─ freeze() on stop
                              │
              Wake Lock API (new) ◄── SessionRecorder (acquire on Start, release on Stop)
              PreSessionGuard.tsx (A) renders the warning callout pre-Start; does NOT itself call wakeLock
```

No algo changes. No schema changes. No migration. Web-only, client-only.

## Hook signature + correctness guarantees

`useCaptureQuality()` is the **single source of truth** for both the live badge (B) and the end-of-session summary (C). They never compute the same thing twice from different code paths.

```typescript
type QualityState = "good" | "weak" | "lost";

type QualitySummary = {
  goodPct: number;     // [0, 1] — fraction of session sample-windows in 🟢
  weakPct: number;     // [0, 1] — fraction in 🟡
  lostPct: number;     // [0, 1] — fraction in 🔴
  windowCount: number; // total 1 s windows aggregated
};

type CaptureQuality = {
  state: QualityState;        // current state, recomputed on each sample
  summary: QualitySummary;    // cumulative since session start (or since last freeze)
  freeze: () => QualitySummary; // returns the snapshot AND marks summary immutable
};

function useCaptureQuality(stream: HRSampleStream): CaptureQuality;
```

### Correctness guarantees

1. **Incremental aggregate.** The summary updates on a 1 s timer by adding **one** new state-window to the running counters. It does **not** re-walk the rolling buffer or re-aggregate from scratch on every render. With ~30 min sessions at 1 Hz, naive re-walking would be 1800 ops per render at session end; incremental is O(1).
2. **Single mutation point.** The hook owns its internal counters via `useRef`. React state holds only the consumer-visible `{ state, summary }` view, updated once per second. No prop drilling of raw RR streams.
3. **Frozen summary is referentially stable.** After `freeze()` is called, all subsequent reads of `summary` return the same object reference. Tested via the freeze-contract case.
4. **Saved page does NOT re-derive.** The saved page reads `sessionStorage["quality:${sessionId}"]` — i.e., the frozen JSON-serialized summary that `SessionRecorder.stop()` wrote. It never sees raw RR samples. This prevents B and C from drifting on threshold changes mid-development: there is one threshold codepath, in the hook.
5. **State derivation pure.** The state-from-window function is a pure function of `(contact, correctionRate, msSinceLastSample)` so it's testable without React. The hook is a thin wrapper that pipes the stream through this function once per sample.

## Inline implementation notes

### `useCaptureQuality()` correction-rate comment

```typescript
// Correction-rate proxy: count consecutive RR intervals where
// |RR_i - RR_{i-1}| / RR_{i-1} > 0.20.
// Source: Lipponen & Tarvainen 2019, "A robust algorithm for heart rate
// variability time series artefact correction using novel beat
// classification" (J. Med. Eng. Technol. 2019). The 20% relative-change
// test is their first-pass artefact gate. Full algorithm has more stages
// (Q1/Q3 thresholds, ectopic detection, missing-beat interpolation) —
// that work runs algo-side. This is the cheap O(n) version suitable for
// live client-side rendering.
```

### Threshold provenance

5% lower bound and 20% upper bound on the rolling-30 s correction rate are **empirical**, not from the literature. They are the design starting point. Verification step 5 (still-sit) is the gate: if a properly-fitted resting session shows >5% correction rate from RSA-driven RR variability alone, raise the lower threshold and re-test. Document the empirical choice inline once verified.

### Wake Lock acquire/release rules

- **Acquire** on session start (user taps "Start session" in `SessionRecorder`)
- **Release** on session end (`SessionRecorder.stop()`)
- **Re-acquire on `visibilitychange === "visible"`** if a session is still active (covers brief tab-switch — when the page goes hidden the browser auto-releases; the lock does NOT restore itself when visibility returns).
- **Listen for the sentinel's `release` event** and re-acquire if a session is still active. This catches iOS battery-saver and other OS-level releases that don't fire `visibilitychange`. Without this listener, a low-battery iPhone silently drops the lock mid-session and the rider never knows.
- The browser implicitly releases the lock on `visibilitychange === "hidden"`, so no explicit release is needed there. Don't try to release a lock the browser already released — it errors.
- Capture-quality state changes (good ↔ weak ↔ lost) **do not** affect Wake Lock lifecycle. Wake Lock is bound to session lifecycle (start/stop/visibility/sentinel-release), not signal quality. Independent concerns.

### Summary cap (freeze contract)

```typescript
// SessionRecorder.stop() {
//   const summary = quality.freeze();          // snapshot, immutable after this
//   sessionStorage.setItem(`quality:${sessionId}`, JSON.stringify(summary));
//   ...
// }
```

After `freeze()`, subsequent samples fed to the hook do not change the summary. Tested explicitly so a future refactor can't break the contract silently.

## Tests

### `web/tests/use-capture-quality.test.ts`

1. **State transitions at the 5% boundary:**
   - Feed 60 samples with 4% correction rate → state stays 🟢
   - Feed 60 samples with 10% correction rate → state flips 🟡
   - Feed 60 samples with 25% correction rate → state stays 🟡 (high correction rate alone never escalates to 🔴 — that's hardware-only)
2. **Lost-on-silence:**
   - Feed samples for 4 s, then no samples for 6 s → state flips 🔴 at 5 s mark
   - Feed samples again → state recovers to 🟢/🟡 depending on correction rate
3. **Hardware contact override:**
   - Feed clean RR with `contact === "no-contact"` → state is 🟡 regardless of correction rate (H10 has no `"bad"` enum value; this is the worst hardware-reported state)
   - Feed clean RR with `contact === "unsupported"` → state is 🟢 (legacy straps that don't report the field)
   - 🔴 is **not** reached via the contact field — only via the 5-second notification silence rule (see #2)
4. **Freeze contract:**
   - Feed 60 good samples → call `freeze()` → snapshot the summary
   - Feed 60 bad samples → assert summary is unchanged from the snapshot (still reflects only the first 60)

### `web/tests/pre-session-guard.test.tsx`

1. **iOS UA shows callout:** mock `navigator.userAgent` to iPhone string → component renders the callout
2. **Non-iOS hides:** mock UA to Android Chrome → component renders nothing
3. **Dismiss persists:** click "Got it" → sessionStorage flag set → re-mount → callout hidden

### `web/tests/wake-lock.test.ts`

1. **Acquire returns a sentinel** when `navigator.wakeLock.request("screen")` resolves; subsequent acquires while a sentinel is held are no-ops (idempotent).
2. **`release` event re-acquires** when a session is active: simulate sentinel firing `release` → assert a fresh `request("screen")` is issued. Pin to "session active" — when no session is active, no re-acquire fires.
3. **Missing API graceful no-op:** when `navigator.wakeLock` is undefined, `acquire()` returns `null`, no exception. Confirms the Bluefy-without-Wake-Lock degraded path stays silent.

## Verification (manual gate, after merge to main)

1. Re-run a 3-min Bluefy session on iPhone with the test account. Mid-session, deliberately loosen the strap → badge flips 🟢→🟡→🔴.
2. End the session. Saved page shows "Recording quality: 🟢 Good signal for X% of session" with X reflecting the loosened-strap window.
3. Lock the iPhone screen mid-session. With Wake Lock active, screen should stay on. (If Bluefy doesn't honor Wake Lock, this verifies the soft-warn copy is sufficient on its own.)
4. Open the URL in iOS Safari (no Bluefy). UnsupportedBanner shows with the new "Open in Bluefy" message.
5. **No-false-alarm check:** Record a 3-min session with a properly-fitted strap, sit still, normal breathing. Badge stays 🟢 throughout — no spurious 🟢→🟡 flips from RSA-driven RR variation. **If this fails, raise the lower threshold from 5% to 7%/10% and re-run.** The exact number isn't sacred; what matters is the badge doesn't lie on healthy resting HRV.

## Deferred — D (BLE auto-reconnect)

Documented in `docs/05-build-plan.md` under Slice 18 (production-gate phase):

> **D — BLE auto-reconnect on disconnect events.** Restore the BLE GATT connection automatically when notifications stop unexpectedly mid-session. Surface a "reconnecting…" banner; resume sample stream on reconnect.
>
> **Prerequisite: real-flake test environment.** Cannot be reliably tested in dev — BLE flakes happen on real horses during real rides, not on a desk. Defer until either (a) we have ≥10 production sessions where BLE drops actually occurred (so we can study the failure modes) or (b) we build a flake-injection test harness (e.g., a synthetic BLE source that drops notifications on cue).

This gates the work behind a real prerequisite so future-Claude or a contractor doesn't pick it up prematurely and ship something untested.
